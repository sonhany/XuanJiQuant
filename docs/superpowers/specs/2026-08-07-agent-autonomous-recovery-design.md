# Agent 自主管控与自治恢复设计

日期：2026-08-07

## 1. 目标

XuanJiQuant 的自动化模拟交易只由 Agent Runtime 管控。数据同步、选股证据、Agent 决策、验证、风险控制和模拟执行形成单一闭环，不再要求用户手工拼接“重新选股、影子验证、启用模拟盘、运行一次 Agent”等恢复步骤。

Agent 发生故障或证据过期时必须失败关闭下单权限，但不能停止自身诊断与恢复能力。系统应自动进入非执行恢复态，完成证据刷新、执行结果核账和安全验证；满足确定性恢复条件后自动回到受控模拟盘。

本设计仅覆盖模拟盘，不开放实盘或券商自动下单。

## 2. 成功标准

1. Agent Runtime 是唯一自动化控制者，不存在第二套 AI、人工日常调度器或手工恢复控制面。
2. 选股证据过期后由 Agent 自主刷新；旧候选不会进入新决策。
3. 维护态仍运行非执行恢复周期，不再把调度器永久阻断在 `agent_runtime_maintenance`。
4. 未知工具副作用、未决订单、活动执行会话、账本不一致、数据过期、verifier 失败或硬风控阻断时不得恢复下单。
5. 确定性恢复条件连续两轮通过后，系统自动恢复 `paper_guarded` 模拟盘。
6. 恢复失败时采用有上限的退避重试，公开唯一、明确、可审计的当前阻断环节。
7. Web 删除“立即重新选股、手动选股、开始影子验证、启用模拟盘、运行一次 Agent”等日常操作入口。
8. 人工只保留紧急停止、撤单、强制减仓和只读审计权限。
9. README 和 `docs/XUANJI_HANDOFF.md` 准确描述模块关系、恢复状态机和安全边界。

## 3. 单一调用链

```text
AI Scheduler
  -> Agent Runtime
      -> Evidence Coordinator
          -> 市场数据新鲜度
          -> 因子/策略快照新鲜度
          -> 选股证据刷新
          -> 宏观与组合风险输入
      -> Recovery Reconciler
          -> 工具调用结果核账
          -> 执行会话与围栏令牌核账
          -> 订单、成交、风险、审计账本核账
      -> Verified Decision Publication
      -> Deterministic Risk Gateway
      -> Paper Execution Session
      -> Execution Ledger
```

数据采集器和风险网关保持独立的确定性安全职责，但不能成为第二个交易决策控制器。Agent 可以调用它们、读取结果并形成决策，不能绕过或降低其约束。

## 4. 自治状态机

### 4.1 状态

- `paper_guarded`：允许经过发布凭证、执行会话、风险网关和围栏校验的模拟订单。
- `recovering`：Agent 正常运行，但所有新增执行资格关闭；允许刷新证据、核账、研究、复盘和生成不可执行决策。
- `maintenance`：仅用于无法安全自动处理的硬阻断；Agent 仍可运行只读诊断和恢复探测，不产生新增订单。
- `emergency_stop`：人工紧急停止状态；自动恢复不得越过，必须由人工解除。

`shadow` 不再作为用户可操作模式。恢复过程内部产生的不可执行 Run 使用 `recovering` 语义，避免把运行模式和人工控制动作混在一起。

### 4.2 转移规则

```text
paper_guarded
  -- 连续执行失败 / 未知结果 / 证据失效 / watchdog 超时 --> recovering

recovering
  -- 一轮恢复验证通过 --> recovering，success_streak + 1
  -- 任一恢复验证失败 --> recovering，success_streak = 0，记录唯一 blocker
  -- 连续两轮通过 --> paper_guarded
  -- 出现不可自动判定硬阻断 --> maintenance

maintenance
  -- 硬阻断消失且恢复探测可确定 --> recovering
  -- 硬阻断仍存在 --> maintenance

任意状态
  -- 人工紧急停止 --> emergency_stop

emergency_stop
  -- 仅人工解除 --> recovering
```

恢复转移必须通过原子配置更新并写入审计事件；不得只修改前端状态或内存标志。

## 5. 证据刷新职责

选股刷新不再绑定“准备下单”这一条件。每个相关 Agent 周期都先调用统一的证据协调器：

1. 计算当前预期交易日和各证据 TTL。
2. 检查全市场日线覆盖率、股票池覆盖率、因子快照、策略快照、宏观快照和选股结果。
3. 对已过期但可自动更新的证据执行单例刷新，禁止重叠刷新。
4. 刷新后重新计算新鲜度，不以“任务返回成功”代替数据日期和覆盖率验证。
5. 只有同一交易日、TTL 内、覆盖率达标的候选池才能发布给 Agent 决策。
6. 刷新失败时清空可用候选视图，保留历史结果仅供审计展示。

盘后生成的选股可以用于研究和恢复验证，但不能直接冒充下一交易日实时证据；下一个可执行周期仍必须重新检查预期日期和 TTL。

## 6. 恢复验证门槛

每一轮恢复验证必须同时满足：

- Agent 数据库和运行时可读写，且没有活动或悬挂 Run。
- 没有 `issued` 或 `active` 的执行会话。
- 没有未核账的 pending、partial 或未知结果订单。
- 所有具有副作用的工具调用都能与订单、成交、风险和审计事实一一对账。
- 市场数据、因子/策略快照、选股证据、宏观输入和组合风险均达到各自新鲜度要求。
- verifier 通过且发布凭证与当前 Run、决策、策略哈希一致。
- authority owner 固定为 `agent_runtime`，epoch、fencing token 和 policy hash 一致。
- kill switch 未触发，硬风控没有阻断。
- 当前没有人工紧急停止锁。

连续两轮均满足才允许恢复 `paper_guarded`。两轮必须具有不同的调度 trigger_id，并重新读取事实，禁止复用同一验证结果。

## 7. 未知副作用处理

`tool_outcome_unknown` 不能被超时、重试或模型判断直接清除。Recovery Reconciler 必须使用确定性事实完成核账：

1. 根据 Run、tool call、decision、session、order 和 ledger 标识定位同一次动作。
2. 找到唯一权威订单/成交结果时，将工具结果收敛为 completed、rejected 或 failed。
3. 找不到结果但能证明动作在副作用发生前失败时，收敛为 failed。
4. 存在多个矛盾权威事实、无法排除重复执行或账本缺口时，保持 maintenance 并产生人工审计事项。

Agent 不得通过重新调用同一副作用工具来“试探”未知结果。

## 8. 调度与并发

- Scheduler 在所有模式下只调度 Agent Run。
- `recovering` 和 `maintenance` 周期禁止申请执行会话。
- 证据刷新、恢复核账和 Agent 周期分别使用单例锁，且同一职责不得重叠执行。
- 调度周期记录开始、心跳、截止时间、完成状态和 blocker。
- 失败重试采用 1、2、5、10、30 分钟阶梯退避，达到 30 分钟后保持该间隔；新数据同步完成事件可以提前唤醒一次恢复检查。
- 盘中不得因为恢复重试产生并发 Agent 执行或重复模拟订单。

## 9. API 与界面

### 9.1 删除的日常动作

- `ai_screen_run`
- `ai_scheduler_run_once`
- `agent_control_start_shadow`
- `agent_control_enable`
- 对应的 Web 按钮、确认框和操作提示

若底层函数仍被内部 Agent 工具复用，应改为内部能力并拒绝公共 API 调用，不保留兼容别名。

### 9.2 保留的能力

- Agent、调度器、证据、恢复、风险和审计只读状态。
- 人工紧急停止。
- 已挂模拟订单撤销。
- 确定性强制减仓。
- 审计导出与回放。

界面统一显示：当前自治状态、当前阻断环节、最近恢复尝试、连续成功轮数、下一次重试时间、证据日期和覆盖率。不得引导用户手工完成 Agent 的职责。

## 10. 故障显示

系统只发布当前最靠前的确定性 blocker，并把其他诊断放入审计详情。例如：

- `市场日线覆盖不足：5001/5203，预期交易日 20260807`
- `选股刷新失败：因子快照仍为 20260806`
- `执行结果待核账：run_id=...，order_id=...`
- `verifier 未通过：publication_policy_hash_mismatch`
- `人工紧急停止已启用`

不得显示“稍后自动恢复”而不给出 Agent 是否正在恢复、下一次时间和实际阻断原因。

## 11. 测试策略

实施必须遵循测试驱动：先补失败测试并确认失败，再写最小实现。

1. 状态机测试：维护/恢复/受控模拟盘转移和连续两轮门槛。
2. 证据协调测试：维护态也能刷新选股；过期候选永不发布；刷新任务单例。
3. 核账测试：唯一权威结果自动收敛，矛盾或缺失事实保持维护态。
4. 权限测试：恢复态无执行会话，Agent 以外 actor 无法取得权限。
5. 调度测试：维护态不再完全停止 Agent；不得重叠 Run 或重复订单。
6. API/UI 合同：公共手工控制动作被删除，界面只展示自治状态和紧急能力。
7. 回归测试：风险网关、verifier、围栏令牌、账本和历史审计事实保持有效。
8. 全量验收：Python、Node 契约、TypeScript、Vite、Web/UI、浏览器控制台、真实 API 状态和性能。

## 12. 迁移与上线

1. 在现有运行状态上先完成只读对账，确认没有活动执行会话或未完成模拟订单。
2. 部署新状态机后把当前 `maintenance/observe` 迁移为 `recovering`，不直接迁移为 `paper_guarded`。
3. 由 Agent 完成两轮确定性恢复验证后自动恢复模拟盘。
4. 迁移过程不修改历史交易、订单、风险和审计事实。
5. 仅重启明确属于 XuanJiQuant 且必须重载的进程。

## 13. 非目标

- 不开放实盘或券商自动交易。
- 不允许 LLM 覆盖硬风控、verifier、围栏令牌或人工紧急停止。
- 不删除或机械篡改历史业务审计事实。
- 不借本次改造重写无关的因子、Qlib、资讯或估值模块。
