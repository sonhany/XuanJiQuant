# Agent 模拟盘部分成交终态设计

日期：2026-08-10  
状态：已批准

## 问题定性

安全降级机制本身正确。缺陷在 Agent-only 模拟执行闭环：市场单部分成交后没有为剩余数量生成可验证终态，`paper_execution_runs` 因而停留在 `running`，工具调用被标记为 `unknown`，自治恢复误把普通交易结果当成未知副作用。

本设计不放宽 verifier、风险网关、执行租约、fencing token 或硬风控，不启用真实交易。

## 目标

1. 部分成交必须持久化为 `filled_qty + remaining_qty`，并在同一执行会话内将剩余数量明确取消；最终订单状态为 `cancelled`，终态原因为 `partial_fill_remainder_cancelled`。
2. `paper_execution_runs`、完成审计事件和 Agent 工具回执必须根据订单、成交、取消三类证据闭环，不得停留在 `running/unknown`。
3. 普通拒单和可证明的部分成交是业务终态，不得触发系统级自治恢复；只有无法证明是否发生副作用的调用才安全关闭。
4. Agent 从恢复态成功晋级后，清零恢复次数、下次重试时间和历史失败基线，使首次交易按新周期判断。
5. 页面准确区分“执行关闭”“自治恢复中”“恢复期影子运行”，恢复时展示原因和预计恢复时间，不再将恢复态写成“未启用”。

## 终态契约

订单的最新持久化事实必须满足以下之一：

- `filled`：`filled_qty == quantity`，关联成交数量合计等于 `quantity`。
- `rejected`：`filled_qty == 0`，没有关联成交，并存在风险拒绝与执行拒绝审计证据。
- `cancelled`（未成交取消）：`filled_qty == 0`，`remaining_qty == cancelled_qty == quantity`，没有关联成交。
- `cancelled`（部分成交后取消）：`0 < filled_qty < quantity`，关联成交数量合计等于 `filled_qty`，`remaining_qty == cancelled_qty == quantity - filled_qty`，并存在同身份的取消审计证据。

完成回执继续使用稳定的订单编号/状态摘要作为幂等哈希输入；数量明细由账本协调器从权威订单、成交和取消事实中验证并返回给 Agent 工具回执，避免破坏既有完成回执兼容性。

## 恢复边界

历史修复只能追加事实，禁止改写既有订单或成交：

- 运行身份、决策、paper run、会话、owner epoch、fencing token、发布声明和订单声明必须完整一致；
- 会话必须已关闭，旧 fencing token 必须已被更高 token 隔离；
- 部分订单的成交合计必须精确等于既有 `filled_qty`；
- 不存在后续订单事实、额外成交或其他歧义；
- 满足条件时追加“剩余数量取消”订单事实和取消审计，再生成唯一完成事件；任一条件不满足则保持安全关闭并报告，不自动猜测。

## 页面语义

- 恢复期间：`Agent 自治恢复中`，显示具体原因与预计恢复时间。
- 观察/影子状态：`恢复期影子运行`。
- 只有显式配置关闭时才显示“执行未启用”。

## 验收

- 部分成交后取消、普通拒单均使账本和工具调用进入 `completed`。
- 完成回执丢失可通过持久化证据恢复，且不重复下单。
- 真正未知副作用仍进入安全关闭。
- 恢复晋级后的首笔模拟交易正常完成，历史失败计数不再污染新周期。
- 当前 2026-08-10 卡住的运行经严格修复后可协调为完成态。
- 相关 Python 测试、全部 Node 契约、TypeScript、Vite 构建、Web/UI 验证及浏览器控制台检查通过。
